Epic: [#3](https://github.com/Mischellin/OpsBrain/issues/3). База — [#2](https://github.com/Mischellin/OpsBrain/pull/2) (v1),
который мержит владелец. Реализуется **стеком из 11 pull request** поверх #2, в порядке зависимостей epic,
мерж снизу вверх (решение владельца 2026-10-04).

## Формат поставки

Один сводный PR на все 11 задач был отклонён: это ~5000 строк поверх неслитого #2 — нереально
ревьюить и опасно откатывать. Вместо этого каждый PR — одна задача, база — ветка предыдущего,
и на каждом стоит `@codex review`. GitHub сам перенаправит базу на `main`, когда #2 смёржится.

## Правило очерёдности

**Новые задачи не начинаются, пока не закрыты P1-замечания `@codex review` в уже открытых PR.**

Причина конкретная: замечания бьют не в детали, а в конструкцию — «id не сверяется со своим хешем»,
«непривязанное доказательство проходит для любого change», «свежесть измеряет время подачи, а не
наблюдения». Этот же приём воспроизведён в `ChangePlan` (#6), потому что был скопирован из
`EvidenceBundle`. Строить седьмой модуль до этого — значит размножать один и тот же дефект по стеку.

## Инварианты (нарушение любого = ревью DENY)

1. Разрешение выдаёт **детерминированный** ApprovalEngine, а не свободный текст модели.
2. Worker и reviewer не имеют прямых production credentials, не меняют active policy, не подделывают
   evidence и не могут самосогласовать свой change.
3. Разрешение действительно только для проверенных plan / arguments / targets / evidence / policy.
   Любое изменение входа делает approval **STALE** и требует нового preflight review.
4. Timeout, quota, disagreement, неизвестный target и недостаток доказательств **не означают PASS**.
   После ограниченных попыток — `BLOCKED_AUTONOMOUSLY`, без повторного запроса `yes`.
5. Успешный return code ≠ достижение цели: нужны фактические post-checks и проверка регрессий.
6. Canary и rollback применяются только при подтверждённой пригодности; непокрытые политикой действия
   блокируются.
7. Claude не является зависимостью. Модели и лимиты конфигурируются, скрытого платного fallback нет.
8. Content-addressed id обязан проверяться против хеша содержимого при каждой верификации. Запись под
   существующим id с пересчитанным digest — не иммутабельность.
9. **Факт, который не установили, — это не факт.** Отсутствующее поле не читается как «не изменилось»:
   policy-факты, `preflight_approvable`, `evidence_ids`, `review_ids` и результат верификации обязаны
   быть установлены явно, иначе решение блокируется. Дефолт, выдающий разрешение, — не разрешение.
10. **Проверка сравнивает два независимых значения.** Binding не сверяется сам с собой: change хранит,
    против чего решали, а gate выводит собственные факты change и сравнивает с ними. Версия policy
    берётся из текущего конфига, а не из того же binding.
11. **Проверка и действие — в одном шаге.** Сохранённый план копируется под новое имя, снимаются права
    на запись, и хешируется и применяется именно копия: применяемый путь и есть проверяемый. Один shell
    не делает две операции атомарными — два открытия одного изменяемого пути это не защита. Границей
    остаётся изоляция раннера: против процесса с тем же uid никакая перестановка команд не помогает, и
    это написано в коде, а не подразумевается.
12. Охрана, которая не применена на пути, — не охрана. Каждый из закрытых P1 был либо «существует и
    задокументирована, но не вызывается», либо «проверяет поле, которого нет».
13. **Модель отвечает, но не решает.** Ровно один вопрос во всём контуре — «изменилось ли то, что
    меняли» — отдан модели, и это postflight. Её словарь исходов физически не содержит «разрешить», а
    `confirmed` требует отчёта проверки, который действительно выполнялся: без измерения максимум —
    `unclear`, и модель при этом не спрашивается вовсе. Отчёт присылает вызывающий, поэтому состояние
    change проверяется отдельно: у отменённого change любой принесённый отчёт зелёный, потому что ни
    одна его проверка ничего не трогала.
14. **Recovery не наследует допуск.** Попытка починить упавший change — это новый change с новым
    plan'ом и новым approval, потому что прежний уже потрачен. Шаг, меняющий инфраструктуру, без
    собственных plan и change отвергается; собирать доказательства можно и без change, это чтение.
    Прогресс меряется отпечатками сбоев и проверенными свойствами: воркер, только что получивший
    «попробуй ещё раз», скажет, что у него получилось.
15. **Откат, который ничего не сломал, — это результат, который надо проверить.** Три раза за этот
    epic «страховка откатом не сработала» оказывались не слабым тестом, а моей же промахнувшейся
    строкой для замены. Проверка отката сама нуждается в проверке: сначала убедиться, что замена
    вообще что-то изменила, и только потом делать вывод.
16. **Тест проверяет тот путь, которым пойдёт клиент.** `review-plan` был объявлен на MCP-поверхности и
    при этом не работал через неё: MCP пре-парсит строковый аргумент в JSON, если аннотация не `str`
    ровно. Все тесты звали Python-метод, поэтому поверхность оставалась непроверенной. Тест, идущий
    через настоящий инструмент, — единственный, который видит такой класс дефектов.

## Проверки

`ruff`, `mypy --strict` и `pytest` проходят в проектном окружении. Live-проверки, требующие реальных
credentials, помечаются как пропущенные, а не выдаются за выполненные.

Два рабочих правила, которые стоили времени и неочевидны:

* **`@codex review` нужно ставить повторно после каждого пуша.** Комментарий, оставленный на старом
  коммите, не обновляется сам, и ревью считается пройденным устаревшей версии. Ревью асинхронно:
  замечания приходят по коду, каким он был *на момент запроса*, поэтому «нет новых замечаний» первые
  минуты после пуша не значит ничего.
* **В стеке push вниз, rebase вверх.** Правка к модулю PR №5 требует перебазировать всё, что выше.
  Порядок: запушить исправленный нижний PR, затем по очереди rebase на `origin/<предыдущий>` и
  force-push. Ребейз в обратном порядке даёт «конфликтующий» PR, хотя конфликта нет.

Ревью находит P1 и на строках, которые только что переписаны: закрытые находки не сходятся, каждый
раунд приносит новые. Это свойство ревьюера, а не признак бесполезности правок.
